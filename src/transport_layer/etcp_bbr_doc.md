# BBR Congestion Control (etcp_bbr)

## 1. Назначение
Адаптация BBRv3 (Bottleneck Bandwidth and Round-trip propagation time) для контроля перегрузки каждого ETCP-линка. Вычисляет cwnd и pacing rate по измерениям bandwidth/RTT и ограничивает их при потерях. Состояния: STARTUP (поиск bandwidth), DRAIN (слив лишнего inflight), PROBE_BW (циклическое зондирование), PROBE_RTT (замер минимального RTT).

## 2. Как пользоваться

### Инициализация
```c
struct bbr bbr_state = {0};
bbr_init(&bbr_state);  // устанавливает STARTUP, сбрасывает все окна
```
`init_cwnd` равен четырём DATA-фрагментам. ETCP задаёт начальное окно `init_cwnd * normalizer->frag_size`,
ограниченное сверху настройкой `bbr_max_cwnd`. MSS здесь — размер DATA без протокольных заголовков,
а не wire-MTU или максимальный размер кадра STCP.

### Вызов на каждом ACK
```c
struct bbr_rate_sample rs = {
    .delivered      = bytes_delivered_in_sample,
    .interval_us    = measurement_interval_us,
    .rtt_us         = latest_rtt_us,
    .acked_sacked   = bytes_acked,
    .lost           = bytes_lost_since_last_ack,
    .is_app_limited = sender_was_limited,
    .tx_in_flight   = inflight_bytes_at_send,
    .prior_delivered = cumulative_delivered_at_send,
};

uint32_t cwnd = current_cwnd, pacing_rate = current_pacing;
bbr_main(&bbr_state, &rs, &cwnd, &pacing_rate, MSS, inflight_bytes, is_cwnd_limited);
// применять cwnd, pacing_rate к линку
```

### Нотификация о потерях и helper старта передачи
```c
bbr_note_loss(&bbr_state);  // вызывать при обнаружении потери
bbr_tx_start(&bbr_state);   // вызывать при возобновлении отправки после idle
```

`bbr_tx_start` доступен как отдельный API, текущая интеграция ETCP его не вызывает.
Базу измерений после пустого flight заново задаёт `etcp_tx_complete`.

### Интеграция с ETCP_LINK
BBR создаётся в `etcp_link_new()` как `link->bbr`. `etcp_tx_ack()` передаёт sample только известной попытки своего линка.
Sample использует неизменные снимки delivered и времени доставки/отправки из `ETCP_TX_ATTEMPT`.
DATA несёт `seq:u32+attempt_no:u16`, ACK возвращает их и задержку формирования ACK тем же каналом.
Номер 1..65535 общий для всех каналов одного seq; внутренняя очередь индексируется ключом `(seq<<16)|attempt_no`.
Исчерпание номера или seq меняет эпоху потока до повторного использования пары; старые DATA/ACK отсекаются сессией.
RTT попытки равен времени до ACK минус эта задержка. Неизвестный/истёкший ID не обновляет BBR/RTT или физическое окно.
Время ACK — обработка ядром после transport/crypto; задержка формирования ACK начинается после обработки DATA ядром.
Так RTT включает очереди workers, занимающие DATA-окно. Ранние метки сокета используются отдельно для RX-полосы.
ACK также содержит общий `ack_created_us`; все `receiver_delay_us` одной секции вычисляются от этого снимка.
`link->ack_timing` сохраняет четыре времени действующей попытки и signed разности часов направлений.
Постоянное смещение часов сокращается при сравнении samples, но абсолютная one-way задержка неизвестна.
`etcp_ack_timing_trend()` возвращает изменения DATA/ACK-задержки через разности интервалов своих часов,
проверяет порядок и возраст пары и указывает ошибку от заданного относительного дрейфа.
Срезы100мс используют горизонт2с и140ppm (каждый узел до±6с/сутки): ошибка до282мкс на дельту.
Сохраняются `ack_trend_interval_us`, `ack_clock_error_us`, `ack_forward_delta_us`, `ack_backward_delta_us`;
нулевой интервал означает непригодную пару. Ошибка от дрейфа не заменяет оценку сетевого джиттера.
Нельзя интегрировать эти изменения в вечный минимум/очередь, теряя растущую неопределённость часов.
Это исходные измерения для диагностики/исследования, они пока не меняют BBR, pacing или RTO.
Старые `tt_last/rt_last` используют коррекцию через RTT/2 и искусственную базу100мс;
для отделения прямой и обратной очередей их использовать нельзя.
`etcp_ack_recv()` освобождает только логическую запись; кумулятивный till не создаёт BBR samples.
Базовый интервал — максимум времени отправки и подтверждения; соседние ACK одной пачки не используются как интервал.
ACK с подтверждениями передаёт также точку приёма пути: накопленные DATA-байты и монотонное время получателя.
Попытка хранит известную точку при отправке. При достоверных положительных дельтах interval дополнительно
ограничивается снизу `ceil(delivered * delta_rx_us / delta_rx_bytes)`. Итог — максимум трёх границ:
коррекция может только снизить BW sample. Часы разных сторон не сравниваются, RTT/min_rtt не меняются.
Неизвестные/нулевые дельты не создают границу; при непредставимом uint32-интервале оценка BW не используется.
`acked_sacked` увеличивает общий счётчик, `delivered` описывает весь интервал и может включать предыдущие ACK.
Окно применяется через `etcp_link_update_inflight_lim`, точный pacing B/s — через `etcp_loadbalancer_set_pacing_rate`.
Shaper списывает DATA-байты, без заголовков и piggyback ACK. При смене ставки остаток долга пересчитывается;
сохраняется не более 1мс накопленного кредита для компенсации округления таймера, без неограниченного burst после idle.
BBR определяет минимум 4*MSS; транспорт ограничивает окно только сверху. `INFLIGHT_LIM_MIN=8192`
задаёт допустимый минимум настройки максимального окна, а не текущее окно.
PROBE_RTT осушает flight до `max(4*MSS, 0.5*BDP)`, выдерживает не менее 200мс и раунд ACK, затем восстанавливает окно.
DATA, отправленные в PROBE_RTT, помечаются app_limited, чтобы низкая скорость осушения не понижала оценку полосы.
ACK-only не ограничивается этим pacing, но проходит общую физическую очередь канала.

Штатное целевое окно PROBE_BW равно `2*BDP + ACK-резерв`, в PROBE_UP добавляются ещё `2*MSS`;
применяются также минимум окна и изученные ограничения inflight. Без отдельного ограничения такие резервы
на канале 2Мбит/с с базовым RTT=20мс давали окно `12060 + 1893 + 2194 = 16147` байт и очередь 44–48мс.

В адаптации ETCP итоговое окно всех фаз PROBE_BW дополнительно ограничено бюджетом очереди:
`max(4*MSS, BDP + BW*queue_budget_us/1000000)`. `BDP` использует min_rtt, а не текущий RTT с очередью.
Резервы ACK/PROBE_UP входят в этот предел. `bbr_init` задаёт `queue_budget_us=20000`; значение можно менять
в uasync-потоке, `0` отключает политику. `queue_cwnd_cap` показывает действующий предел в DATA-байтах;
`0` означает, что ограничение не активно. Callback окна получает уже ограниченный результат, включая fast path.

`cwnd_snapshot` хранит реальные промежуточные значения последнего вызова: входное окно, рассчитанную цель,
окно после цели, предел inflight-модели, окно после него и итог после бюджета очереди. `target/model_cap=0`
означает пропущенный расчёт. Это только диагностика; значения не участвуют в управлении окном.
`test_etcp_multipath` сохраняет их с очередями, BW/inflight bounds, RTO и счётчиками ограничений каждые100мс
при `UTUN_MULTIPATH_DIAG=path.csv`; вывод буферизуется до drain. Разбор большого джиттера и контрольные
прогоны описаны в `doc/crypto_transport_perf.txt`; поправка `2*jitter` пока не принята в рабочий алгоритм.

В STARTUP минимум достоверных RTT целого ACK-раунда сравнивается с `min_rtt+queue_budget_us`.
Устойчивое превышение завершает разгон и включает DRAIN; одиночный пик или отключённый бюджет этого не делает.
Первый достоверный RTT задаёт начальный pacing по окну `4*MSS`, независимо от размера первого служебного DATA.

Это целевая задержка по оценке полосы, а не гарантия физического времени очереди. Окно STARTUP и DRAIN
не ограничивается формулой бюджета. Минимум 4*MSS может требовать больше 20мс сериализации;
при неизвестном min_rtt или нулевой оценке полосы дополнительный предел не применяется.
Изменение пропускной способности, jitter, обратная очередь и потери ACK могут делать оценку неточной.
После изучения полосы меньший предел может ограничивать скорость; реальную очередь отдельно измеряет multipath-тест.

### Тестирование
Поле `now_tb` позволяет подменять реальное время (`get_time_tb()`) на заданное — при `now_tb == 0` используется `get_time_tb()`, иначе управляемое значение. `on_cwnd_update` — callback для отслеживания изменений cwnd в тестах.

### Фиксированная точка
- `BBR_SCALE = 8` — масштаб для gain-коэффициентов (2.77 = 2.77 * 256)
- `BW_SCALE = 16` — байты/мкс Q16; повторного умножения на MSS при получении B/s и BDP нет
- MSS используется для минимального окна и бюджета зондирования. Pacing API ограничен UINT32_MAX B/s, переполнения насыщаются
- Все внутренние вычисления в фиксированной точке, преобразование в реальные единицы через `bbr_rate_bytes_per_sec()`

## 3. API

### Структуры

**`struct bbr_rate_sample`** — сэмпл доставки для одного ACK
| Поле | Назначение |
|------|-----------|
| `delivered` | байты, доставленные за измерительный интервал |
| `interval_us` | Измерительный интервал, мкс; в ETCP max(send,ACK,приёмная граница); 0 — нет оценки скорости |
| `rtt_us` | последний измеренный RTT |
| `acked_sacked` | байт подтверждено (+SACK) |
| `prior_delivered` | кумулятивно доставлено при отправке подтверждаемого пакета (для детекта round) |
| `tx_in_flight` | inflight на момент отправки подтверждённых пакетов |
| `lost` | потерянные байты с последнего ACK |
| `is_app_limited` | при отправке не было ожидающих данных приложения либо шёл PROBE_RTT |

**`struct bbr`** — состояние BBR на линк (контракт в etcp_bbr.h).

### Функции

**`void bbr_init(struct bbr* bbr)`** — инициализация: STARTUP, сброс окон, `min_rtt_us = ~0U`, `bw_lo = ~0U`, `inflight_hi/lo = ~0U`.

**`void bbr_main(struct bbr* bbr, const struct bbr_rate_sample* rs, uint32_t* cwnd_out, uint32_t* pacing_rate_out, uint32_t mss, uint32_t inflight_bytes, int is_cwnd_limited)`** — главный вызов на каждый ACK. Обновляет delivered, детектит начало раунда, вычисляет sample_bw, обновляет модель (congestion signals, ack aggregation, full_bw, drain, cycle, min_rtt), применяет gains, вычисляет cwnd и pacing rate.

**`void bbr_note_loss(struct bbr* bbr)`** — помечает потерю в текущем раунде/цикле.

**`void bbr_tx_start(struct bbr* bbr)`** — отмечает возобновление передачи после idle, сбрасывает `ack_epoch`.

### Режимы и циклы

| Режим | Описание |
|-------|---------|
| `BBR_STARTUP` (0) | Экспоненциальный рост cwnd (gain 2.77 pace, 2.0 cwnd), пока не найден bottleneck |
| `BBR_DRAIN` (1) | Слив избыточного inflight (gain 1000/2885 ≈ 0.35 pace) |
| `BBR_PROBE_BW` (2) | Основной рабочий режим, циклическое зондирование |
| `BBR_PROBE_RTT` (3) | Осушение flight до max(4*MSS, 0.5*BDP), удержание >=200мс и раунд ACK |

Циклы внутри `BBR_PROBE_BW`:
- `BBR_BW_PROBE_UP` (1.25× pace) — зондирование большей полосы
- `BBR_BW_PROBE_DOWN` (0.75× pace) — слив после зонда
- `BBR_BW_PROBE_CRUISE` (1.0× pace) — крейсерский режим
- `BBR_BW_PROBE_REFILL` (1.0× pace) — восполнение перед новым зондом
