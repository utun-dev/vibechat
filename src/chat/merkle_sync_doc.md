# merkle_sync

Сверка merkle_sync.h и этого документа с реализацией завершена 26.10.2026.
Проверены общий движок, адаптер MEMBERS, зависимые состояния FEEDBACK и перенос истории MESSAGES;
найденные дефекты исправлены. Остальные модули чата проверяются отдельно.
Объём, результаты и ограничения: [отчёт](../../doc/member_merkle_audit_findings.txt), разделы 6, 9 и 13.

## Разделение ответственности

- merkle_tree: производный индекс SQLite, хеши листьев и родителей.
- merkle_sync: обмен, backpressure и жизненный цикл сессий.
- member_sync: формат участников, подписи, версии, применение страниц.
- chat_feedback: подписанные состояния реакций/ответов, ver, отмены и применение страниц.
- db_sync: подписанная история MESSAGES, первоначальная проверка SQLite, страницы и PUSH/ACK.

Движок не знает CHAT-групп. Namespace — каноническая десятичная строка uint64_t.
Все операции выполняются в одном потоке uasync экземпляра.
Сессия определяется тройкой (peer, dataset, namespace). MEMBERS=0, FEEDBACK=1, MESSAGES=2.
В индексе SQLite namespace хранится как `dataset:channel_id`; корни наборов независимы.

## Дерево и транзакции

Корень имеет уровень 0. Уровни 1–5 разбивают старшие 25 бит ключа на группы по 5 бит.
Полный ключ курсора — 32 байта с лексикографическим порядком; ветвь задаётся первыми 8 байтами.
Для участника ключ — полный Ed25519 устройства. Для feedback — SHA256 идентичности записи, для истории — message_id.
Совпадение первых 64 бит не объединяет записи и не пропускает их при пагинации.
SHA256 листа: `0x4d || level:1 || item_hashes`, записи упорядочены по unsigned key.
SHA256 родителя: `0x4d || level:1 || child_hash[0] || ... || child_hash[31]`.
Хеш пустого поддерева — 32 нулевых байта; строка индекса для него отсутствует.
Пересчитывается один лист и его предки, до первого неизменившегося хеша.

Индекс создаётся заново при init и заполняется моделью из исходных записей.
Модель меняет данные и вызывает recompute_path в одной транзакции, затем changed после commit.
Без внешней транзакции recompute_path создаёт savepoint и уведомляет самостоятельно.
Ошибки не заменяются пустыми страницами или нулевыми хешами.

## API

init принимает service и data_ops начальной модели MEMBERS. register добавляет другие наборы.
Каждая модель задаёт update_bucket_hash, get_page и способ применения страницы,
необязательные validate_peer, can_run, on_result и finish.
update_bucket_hash добавляет хеши одного листа в переданный SHA256-контекст.
get_page получает ёмкость буфера и курсор; возвращает размер, последний ключ и флаг продолжения.
Модель задаёт длину обязательного нулевого хвоста курсора в cursor_zero_tail. Для MEMBERS все 32 байта ключа значимы. Некорректный курсор входящего QUERY или PAGE даёт MT_ERR_PROTOCOL.
Ошибка формирования локальной страницы, включая непродвигающийся next при more=1, даёт MT_ERR_IO.
apply_items проверяет весь формат и применяет страницу вместе с индексом атомарно.
Вместо apply_items можно задать apply_page: он также получает prefix, after, next и more
и проверяет принадлежность фактических записей запрошенному листу/диапазону.
validate_peer разрешает обмен только при возврате 1; проверяется и перед отправкой.
can_run задаёт политику работы модели; без него peer_sleep_phase откладывает обмен.
История разрешает sound_on для спящего пира. recheck_peer завершает запрещённые
попытки, освобождая пакет/waiter/таймер и сохраняя подписку для последующего start/changed.
on_result получает результаты всех раундов, включая автоматические, до пользовательских callbacks;
он может отменить сессию. Указатели и список пользовательских callbacks захватываются заранее.
finish проверяет отложенные зависимости модели перед подтверждением корня.

При работе через SQL worker сессия получает контекст begin_pull после успешного внешнего COMMIT.
Если за это время сессию отменили, движок удаляет подтверждённые промежуточные записи через abort_pull.
При ошибке транзакции движок освобождает память контекста. Этот ID может снова выдать SQLite.
При неопределённом результате COMMIT оставшиеся промежуточные записи удаляет очистка при запуске.

Вместо непосредственного apply_items модель может задать все четыре callback:
begin_pull, stage_page, commit_pull, abort_pull. begin_pull создаёт ненулевой контекст;
stage_page получает также prefix и оба курсора страницы и накапливает данные.
commit_pull применяет результат после завершения своего прохода, до TURN/CHECK.
В MEMBERS вызову предшествует подтверждение корня источника.
abort_pull освобождает контекст как после commit, так и при restart/cancel/ошибке.
В этом режиме apply_items необязателен; атомарность публикации обеспечивает модель.
Необязательный publish_pull вызывается только после успешного commit на выходе из
обработчика пакета. Контекст уже отсоединён: уведомления могут отменять сессии;
после них abort_pull освобождает контекст. Ошибка commit вызывает только abort_pull.

start подключает (dataset, namespace) к текущему соединению и запрашивает контрольную точку.
Повторные start объединяются, обход не сбрасывается, каждый принятый callback вызывается один раз.
После подключения изменения синхронизируются автоматически. Broadcast/send-back не требуются.
MT_OK означает совпадение корней конкретного раунда, а не отсутствие будущих изменений.

cancel отменяет только заданный dataset/peer/namespace.
cancel_ns отменяет все datasets канала, cancel_peer — все datasets пира.
cancel_dataset_ns/cancel_dataset_peer ограничивают отмену выбранным набором.
Все cancel и destroy освобождают запросы без callback.
DOWN/DELETE/REINIT завершают запросы ошибкой и освобождают сессию.
После восстановления соединения интеграционный слой повторяет start.
Callback может отменить сессию; уничтожение всего экземпляра следует отложить через call_soon.

## Обмен

Лексикографически меньший Ed25519 ведёт раунд; второй запрашивает его через WAKE.
WAKE также перезапускает незавершённый раунд после cancel/start второго узла.

1. BEGIN(new round) → READY.
2. Ведущий запрашивает хеши детей и обходит различающиеся ветви в глубину.
3. Лист запрашивается страницами с возрастающим курсором.
4. TURN меняет направление: второй узел выполняет такой же pull.
5. Второй проверяет finish и отправляет CHECK(root).
6. Ведущий сверяет корень, проверяет finish и отправляет DONE(root).
7. Второй сверяет DONE со своим текущим корнем.

Ведущий сообщает MT_OK после передачи DONE в надёжный транспорт, если локальная ревизия
не изменилась после проверки. Второй сообщает MT_OK после проверки полученного DONE.
Изменения во время обмена вызывают следующий раунд.
Два завершённых раунда с одной и той же несовпадающей парой корней дают MT_ERR_CONFLICT.
Детерминированное слияние обеспечивает модель; движок не выбирает победителя конфликта.

Ожидается только один ответ QUERY. Стек — максимум шесть кадров с сохранёнными соседними ветвями.
Номера запросов проверяются, ответы другого раунда игнорируются.
Повторную передачу обеспечивает ETCP, отдельных таймеров повторов нет.
Некорректные BEGIN, WAKE и ERROR отбрасываются до создания сессии и до очереди SQL.
На исходящий пакет (включая ожидание backpressure) и ожидание ответа действует таймер
30 секунд. При прогрессе он перевзводится до ближайшего срока: 30 секунд без прогресса
или 10 минут с отправки BEGIN у ведущего и приёма BEGIN у отвечающего. Истечение
завершает раунд с MT_ERR_TIMEOUT. Завершившаяся запись SQLite публикуется даже при
истечении срока, продолжение протокола для этого раунда отменяется.
CHAT после сверки листьев запрашивает недостающие блоки до TURN или CHECK. В каждый
момент открыт один запрос, связанный с текущим ETCP-соединением, обоими токенами
раунда и номером запроса. Ответ применяется к зафиксированному диапазону или
доказательству. Если заявленная зависимость источника изменилась, он отвечает
MT_ERR_STALE. После MT_ERR_STALE или MT_ERR_TIMEOUT ведущий начинает новый CHAT-раунд
с задержкой, когда удалены временные записи его предыдущего прохода.
Для одного CHAT pull временные строки голов и курсоров срезов ограничены 32 МиБ
учитываемых данных. При превышении страница откатывается, обе временные таблицы
очищаются по ID прохода, уже подтверждённая история сохраняется. MT_ERR_LIMIT
завершает проход без автоматического повтора, в том числе при блокировке отправки ERROR.
В каждом направлении MEMBERS получатель фиксирует свой корень перед обходом.
Источник фиксирует свой корень в той же транзакции, в которой читает первую ветвь.
Они проверяют свои корни при чтении ветвей. Получатель проверяет доказательства
хешей и полное содержимое запрошенных листьев, сохраняя записи во временных таблицах SQLite.
В конце прохода он отправляет SOURCE_CHECK с корнем полученных данных. Источник
сравнивает его со своим зафиксированным и текущим корнями и отвечает SOURCE_OK.
Получатель сверяет ответ и перепроверяет свой корень в окончательной WRITE.
MEMBER_ADMIN (dataset 5) использует тот же проход с подтверждением корня.
После MT_ERR_STALE или MT_ERR_TIMEOUT в двустороннем обмене ведущий запускает новый раунд
после очистки staging с задержкой от 1 до 30 секунд. Ведомый повторяет WAKE при таймауте
ожидания первого BEGIN, а при FILE/RW также на этапе DONE. В FILE/RW временная блокировка
SQLite (BUSY/LOCKED) даёт локальный MT_ERR_DB_RETRY. Сторона, получившая ошибку, использует
ту же задержку перед новым BEGIN (ведущий) или WAKE (ведомый). При временной блокировке
очистка staging повторяется по тому же receive_id. NCD удерживает транспорт до повтора.
Результат исходного запроса доставляется один раз, результат автоматического раунда получает on_result модели.
После успешной WRITE обычный обмен продолжается TURN/CHECK/DONE,
а однонаправленный запрос завершается. Объединённый корень может включать локальные записи.
Периодического bg_check и отдельного WAL-таймера в текущем merkle_sync нет.

При отзыве допуска модели revalidate_peers завершает ожидания этого пира MT_ERR_DATA,
освобождает подготовленный пакет/таймер/waiter, но сохраняет подписку в FAILED.
После восстановления changed запускает новый раунд: ждать ответа на ранее отброшенный пакет не нужно.
Вызовы выполняются после commit; done callback может отменить сессию без use-after-free.

## Wire

Заголовок v5 имеет 79 байт. Поля идут в порядке `service:1 | group_key:32 | type:1 | round:8 | request:4 | dataset:1 | round_id:16 | accept_id:16`. Для CHAT group_key содержит полный Ed25519 группы.
`round` — диагностический счётчик. Свежий `round_id` создаёт инициатор BEGIN, свежий `accept_id` добавляет ответчик READY.
Все дальнейшие пакеты проверяют оба идентификатора, номер запроса и фазу. После cancel/start старый BEGIN может получить
новый challenge, но прежние PAGE/DONE/ERROR не соответствуют новому accept_id. Дубликат BEGIN не меняет текущий challenge.
WAKE содержит нулевые идентификаторы, BEGIN — нулевой accept_id. Старый wire не поддерживается.
Ошибка генератора случайных байтов завершает запрос MT_ERR_IO до установки нового раунда.
Дубликат READY с тем же accept_id не перезапускает текущий обход.
Все целые big-endian. Максимальный пакет вместе с заголовком — 16384 байта.
Типы 0x10–0x19: WAKE, BEGIN, READY, QUERY, HASHES, PAGE, TURN, CHECK, DONE, ERROR.
Типы 0x1a и 0x1b: DEP_QUERY и DEP_REPLY.
Типы MEMBERS и MEMBER_ADMIN 0x1c и 0x1d: SOURCE_CHECK и SOURCE_OK.

| Тип | Payload |
|---|---|
| WAKE, BEGIN, READY, TURN | пустой; request=0; у WAKE также round=0 |
| QUERY | level:1, prefix:8, after_valid:1, after:32 |
| HASHES | 32 хеша детей по 32 байта в порядке индексов |
| PAGE | more:1, next:32, model_data |
| CHECK, DONE | корень 32 байта, request=0 |
| SOURCE_CHECK, SOURCE_OK | корень прохода MEMBERS, 32 байта, request=0 |
| ERROR | положительный код ошибки 4 байта; request=0 |
| DEP_QUERY | от 1 до 112 байтов параметров зависимости |
| DEP_REPLY | данные зависимости с номером соответствующего DEP_QUERY |

В CHAT первый байт запроса и ответа задаёт зависимость. Запрос хвоста (1) содержит
Ed25519 автора, первый и последний допустимые номера, номер заявленной головы
и её хеш. Запрос развилки (2) содержит Ed25519 автора, номер развилки и два хеша
в возрастающем порядке. Ответы состоят из блоков с двухбайтовыми длинами.
Запрос предка среза (3) содержит ID среза, номер и хеш блока. Ответ содержит один блок.
Номера блоков в запросах занимают 8 байтов, ID, ключи и хеши — 32 байта.

Курсор продолжения должен возрастать и принадлежать запрошенному листу.
Длины, состояние, тип, префикс и номер запроса проверяются до применения.
Формат model_data определяет адаптер. Старый протокол не поддерживается.

## Очереди, диагностика, тесты

Сессия удерживает ETCP_CONN и исходную очередь. У неё один подготовленный пакет,
один waiter и один отложенный вызов. Передача идёт только после разрешения waiter.
Изменения объединяются флагом dirty; неограниченной out-очереди нет.
Отмена снимает ожидающий и отложенный callback waiter независимо от links_up.
Если к моменту вызова waiter очередь ETCP снова заполнена, сессия сохраняет пакет
до следующего уведомления. При DB_ASYNC_FULL CHAT повторяет постановку того же SQL-шага
с задержкой. Снимок и проверка допуска выполняются при фактическом dispatch.

Категория member_sync: INFO — attach, начало/завершение раунда, detach;
DEBUG — TX/RX, номера запросов, размеры, состояние; ERROR — причина отказа.
Ведущий выводит счётчики переданных и полученных байтов при подтверждении.

test_merkle_sync проверяет индекс, односторонний start, двустороннее слияние, несколько узлов,
параллельные изменения, большой лист с пагинацией и автоматическое обновление.
test_merkle_protocol проверяет ошибочные пакеты/курсоры, сохранение соседних ветвей,
отмену waiter, ошибки apply/SQLite, backpressure, disconnect и повторное подключение,
изоляцию datasets и пагинацию разных ключей с одинаковым 64-битным префиксом.
Дополнительные регрессии: cancel/start и старые PAGE/DONE/ERROR, дубликаты BEGIN/READY,
отказ RNG обеих сторон, политика спящего пира и восстановление допуска на прежнем соединении.
История и её ограниченные транзакции описаны в [db_sync_arch.md](db_sync_arch.md).
test_chat_feedback проверяет подписи, монотонный ver, отмены, старые записи,
конфликты одного ver, атомарность страниц, восстановление дерева и удаление канала.

## Подписанные состояния feedback

Таблица feedback_<channel> хранит проекцию подписанных блоков журнала CHAT.
Уникальность реакции или ответа задаёт тройка (message_id, author_ed, kind).
author_ed — 32 байта Ed25519 из заголовка блока. ver — номер этого блока в цепочке автора.
Блок указывает message_id через поле scope. Тело содержит тип действия CHAT_FEEDBACK,
kind и канонические байты состояния. kind=1 — реакция, kind=2 — ответ.
Пустое состояние означает отмену.

Узлы синхронизируют головы журналов и недостающие блоки через MT_DATA_CHAT_LOG.
Получатель проверяет подпись, синтаксис действия и связь с предыдущим блоком до сохранения.
Синтаксически неверный блок не меняет цепочку или Merkle-инвентарь. Проекция проверяет
поколение допуска автора и применимость действия к текущему состоянию. Если неверен
вложенный манифест файла, блок сохраняется, а сообщение остаётся вне проекции.
При конфликте UUID уже зарегистрированного файла сообщение сохраняется без новой ссылки на объект.
При отзыве допуска граница подтверждается подписанным срезом группы.
Запись таблицы проекции ссылается на удостоверяющий блок по Ed25519 автора и номеру.
Снимок опроса передаёт Ed25519 ответивших в поле author_id (64 lowercase hex).

## Опросы и реакции

`chat_poll_codec` задаёт общий каталог 16 эмодзи и канонические кодеки.
Реакция: count=1 и номер эмодзи; автор выбирает только один смайлик на сообщение.
Выбор другого смайлика заменяет предыдущий с новым ver; повторное нажатие отменяет реакцию.
Ответ: count:1, отсортированные уникальные номера пунктов, custom_len:2, UTF-8 текст.
Пустой набор/ответ кодируется нулевой длиной. Собственный текст — максимум 1024 байта.
Структурно неверные состояния отклоняются до записи; семантически неверные подписанные ответы
сохраняются, но исключаются из подсчёта, чтобы порядок получения опроса не менял Merkle-корень.

Опрос — подписанное сообщение `content_type=poll`, data=`b64:` + URL-safe base64.
Wire v1: version:1=1, mode:1 (single=1/multiple=2), allow_custom_answer:1, option_count:1,
затем вопрос и варианты как length:2 + UTF-8. Числа big-endian, весь poll максимум 2048 байт.
Вопрос — максимум 512 байт, 2–32 разных непустых варианта по 256 байт.
Порядок вариантов неизменяем; номер варианта — индекс с нуля.
single разрешает один вариант либо собственный текст, multiple — варианты и необязательный текст.
Изменение ответа заменяет его целиком с ver+1; нулевой ответ отменяет голос.

message_id сохраняется в msg_<channel> с UNIQUE-индексом:
SHA256(`utun-chat-message-v5` || BE64(timestamp) || author_ed25519[32] || nonce[16] || generation[32]).
ID не меняется при правке текста; MESSAGES заменяет запись только при большем ver.
Конверт и подпись версии описаны в [db_sync_arch.md](db_sync_arch.md).
Этот ID одинаков на всех узлах и возвращается API сообщений и результатом публикации опроса.
Получение исходного сообщения повторно проверяет отложенные ответы. Пользовательские результаты
вычисляются по последним допустимым непустым состояниям; проценты — от числа ответивших.
При нескольких вариантах сумма процентов может превышать 100%.

Команды `poll_create`, `vote`, `react`, `feedback`, `reaction_catalog` разбираются единым
chat_feedback_command в потоке ядра. Desktop и Android получают адресные события FEEDBACK_CHANGED
и коррелированные результаты FEEDBACK_RESULT; GUI-поток не пишет подписанные данные.
При старте чата запускается member_sync по известным онлайн-пирам, затем feedback sync:
это нужно и при restart поверх сохранившегося UP-транспорта, когда нового conn_up не будет.

test_chat_poll проверяет пользовательский API, кодеки, ограничения, отмены и отложенный опрос.
test_chat_poll_network проверяет A ↔ B ↔ C, Unicode-ответ, реакцию, остановку/запуск C,
исключение A, позднее подключение D без неактивной истории и возврат A.
После возврата D получает сохранённые состояния, A передаёт новую отмену через прежний UP-транспорт;
результаты и корни активного набора сходятся. test_chat_feedback проверяет также purge,
межканальную зависимость ключа, отсутствие уведомлений от профиля и rollback SQL/index/commit.
