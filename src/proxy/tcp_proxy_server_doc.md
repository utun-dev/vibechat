# TCP proxy server (exit)

`tcp_proxy_server.c/h` открывает обычный TCP к IPv4-назначению по CONNECT ingress-узла
и передаёт данные через роутер группы. Формат описан в
[proxy_protocol.h](proxy_protocol.h), контракт API —
[tcp_proxy_server.h](tcp_proxy_server.h).

## Инициализация и ресурсы

Контекст встроен в `inst->tcp_proxy_server`. `init(inst)` обнуляет его, читает
`config->global.tcp_proxy_server_enabled`, при включении регистрирует сервис
`ETCP_RT_ID_TCP_PROXY_SERVER` (0x04).
NULL inst даёт -1; отсутствие config или отключённый сервер дают 0 без binding.
Занятый binding/ошибка bind возвращает -1; enabled выставляется только после успеха.
Повторный init отклоняется. Общие UDP/ICMP создаёт и уничтожает instance независимо от TCP-модулей.

Секция `[tcp_proxy_server]` включает exit. Без `allowed_group` разрешена только UTUN.
Каждая строка `allowed_group` добавляет одну группу к явному списку. Чтобы обслуживать
UTUN и CHAT, укажите обе группы. CHAT задаётся десятичным ID канала.

```ini
[tcp_proxy_server]
allowed_group=utun
allowed_group=dd9d33df43dfd02381612a908ff3e1296e4862b7121d590a12edefbae7d73d28
```

Для CHAT exit проверяет членство собственного узла и пира. TCP, UDP и ICMP отвечают
в группу запроса. TCP-поток определяется группой, конечным пиром и `stream_id`.
Повторный CONNECT с таким же ключом получает ERROR.

### Лимиты

В `[tcp_proxy_server]` параметр `max_flows` задаёт общий предел (по умолчанию 1024),
а `max_flows_per_node` — предел по конечному node_id во всех группах (по умолчанию 256).
Каждый подключающийся или открытый TCP-поток, UDP-поток и ожидающий ICMP-запрос занимает одно место.
Квота проверяется перед созданием ресурса в потоке uasync. Новый CONNECT при отказе получает ERROR,
новый UDP-поток или ICMP-запрос отбрасывается. Повторная датаграмма существующего UDP-потока
проходит при заполненной квоте. Удаление записи сразу возвращает место.

## Connect и обмен данными

CONNECT содержит четыре байта IPv4-адреса и два байта порта в сетевом порядке.
TCP exit включает неблокирующий режим и применяет явно заданные параметры до `connect()`.
`bind_ip` задаёт локальный IPv4-адрес, `netif` и `so_mark` выбирают устройство и метку Linux,
`fib` задаёт таблицу FreeBSD. Нулевые метка и FIB оставляют системный выбор.
Неверное значение или неподдерживаемая на платформе настройка отклоняет конфиг.
Имя интерфейса хранится до подключения. Если ОС не может применить настройку, попытка
завершается с ERROR. Следующий CONNECT проверит состояние сети заново.

Таймаут `connect_timeout` по умолчанию составляет 2000 мс, 0 отключает таймаут.
При немедленном успехе или подтверждении через SO_ERROR exit возвращает CONNECTED.
При отказе создания сокета, его настройки, регистрации, подключения или таймауте
сервер освобождает ресурсы потока и отправляет ERROR. UDP и ICMP используют собственные сокеты.

DATA клиента проверяется через proxy_flow_receive, копируется в pool-backed write_queue TCP.
Кредит WINDOW возвращается после опустошения **и write_queue, и write_buf**,
то есть после передачи принятой порции в OS TCP, а не при получении ETCP-пакета.
Счётчик bytes_sent увеличивается до проверки/постановки в очередь и не является
числом реально доставленных destination байтов.

Данные destination берутся из read_queue и отправляются через proxy_flow_send (force=0).
При блокировке entry возвращается в начало read_queue. Для ошибки router ставится
send-ready waiter; отсутствие ready/кредита (-2) ждёт CONNECTED/WINDOW.
Safety-net 500 мс возобновляет drain с обычным force=0, не обходит окно/очередь router.
Чтение tcp_io ограничивается его очередью. Отдельных tx_buf/pause_buf у сервера нет.

## FIN, CLOSE и ERROR

FIN destination отправляется клиенту только после опустошения read_queue.
Ожидание write_queue противоположного направления для этого не требуется.
FIN клиента отмечает flow.fin_received и ставит FIN-маркер в OS write_queue:
shutdown(SHUT_WR) следует за всеми ранее принятыми DATA. Дальнейшие DATA после FIN отклоняются.
Когда FIN отправлен, принят встречный FIN и OS TCP отправил локальный FIN,
в write_queue ставится close-маркер.

CLOSE клиента устанавливает cli_closed, паузит OS-чтение и отбрасывает read_queue.
При установленном TCP close-маркер ждёт ранее принятые записи write_queue;
ещё не подключённый поток освобождается сразу. ERROR немедленно уничтожает поток,
не ожидая дренажа потенциально зависшего upload.

Общий proxy_flow повторяет только pending CONNECTED/WINDOW/FIN через 500 мс.
CLOSE/ERROR не имеют экспоненциального backoff или собственной очереди server retry.
OS error callback удаляет поток и делает отдельную попытку отправки ERROR;
conn_free сам по себе не отправляет control-сообщение.

## Диспетчеризация и очистка

recv_cb владеет entry/dgram и освобождает их после обработки. Длина команды и группа проверяются до поиска потока.
Peer берётся из метаданных router, а не из физического conn.
Уведомление router без payload (26 байт) удаляет только потоки данного peer в группе уведомления.
Это локальное CLOSE_ALL/restart/close-событие канала, не отдельная 9-байтовая команда proxy.

conn_free сразу помечает freed, удаляет поток из списка, отменяет waiter/control retry,
DATA retry и диагностический таймер, уничтожает TCP. Память потока и TCP-соединения
освобождается после возврата из синхронных обработчиков. Обе записи для отложенного
освобождения резервируются до connect, поэтому закрытие работает и при нехватке памяти.
Указатель нельзя использовать как живой поток после conn_free.

destroy выключает сервер и снимает только его binding; общие UDP/ICMP-контексты сохраняются.
Instance останавливает proxy до разборки UTUN-группы и транспорта; ua обрабатывает отложенные free.
Все операции выполняются в uasync. Каждую секунду диагностический таймер пишет
размеры TCP-очередей, наличие write_buf, кеши пулов и OS socket buffers на уровне proxy=trace.
