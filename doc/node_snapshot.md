# Подписанная запись узла

`TOPO_NODE.timestamp` — версия всей подписанной записи, а не отдельного адреса.
Узел-владелец назначает Unix microseconds, строго больше предыдущей сохранённой
версии. Имя, тип, активность, адреса, метаданные сокетов, REALITY и подпись
заменяются вместе. Timestamp входит в подпись. Групповые пути и подсети
остаются в `TOPO_GROUP_NODE` и не являются частью общей записи узла.

В NODEINFO секции подсетей присутствуют только при `TOPO_FLAG_SEND_SUBNETS`.
Без флага оба счётчика подсетей равны нулю; противоречащий этому заголовок отклоняется.
Parser проверяет точную длину пакета и проходит все присутствующие секции независимо
от запрошенных `out_*`: например, `out_subnets=NULL` отключает создание объектов подсетей,
но сохраняет проверку префиксов и правильное положение следующего hop-list.
Выходы выдаются только после полного успеха; при ошибке они обнулены, частичные объекты
освобождены. Подпись и допустимость пути проверяются после структурного разбора.

Получатель проверяет подпись до изменения реестра или маршрутов. Более свежая
запись заменяет старую целиком, включая пустые списки адресов. Старые записи
игнорируются; разные подписанные записи с одинаковым timestamp — конфликт.
Повторное BGP-объявление может обновить путь, но не содержимое общей записи.
8-битный `ver` сохраняется как диагностический счётчик; свежесть определяется
только timestamp.

Локальный узел группы готовится до удаления прежнего `local_node`: сравниваются сами адреса
и префиксы подсетей, включая замену при прежнем количестве. При отказе памяти, подписи или
конфликте IPv4-маршрутов прежние узел и маршруты сохраняются. Подсети CHAT не публикуются.
`topo_group_update_my_nodeinfo` возвращает число IPv4-подсетей, для CHAT — 0, при ошибке — -1;
рассылку подготовленного NODEINFO выполняет вызывающий.

Живая телефонная занятость передаётся без изменения структуры NODEINFO: в существующем
`flags` бит `0x04` означает известное состояние, `0x08` — занятость звонком.
Это групповые флаги `TOPO_GROUP_NODE.phone_status`, как флаг рации `0x02`;
они не входят в подпись общей записи и используются только для цвета трубки в GUI.
Без разрешения Android, при выключенной публикации и после ухода узла статус неизвестен.
Решение о начале вызова принимает адресат по локальному состоянию ОС, а не по BGP-подсказке.
Изменения публикуются обычной новой версией NODEINFO во всех CHAT-группах; отдельного опроса и таймера нет.

Профиль endpoint в SOCKMETA содержит независимые `mapping` и `inbound`, источник `source`.
ID и время измерения не передаются: последний успешный профиль действует до
явного изменения endpoint или подтверждённого нового результата. Повторная
проверка с тем же результатом не меняет NODEINFO. Все поля SOCKMETA — отдельные байты;
границы списков metadata/адресов/REALITY также входят в каноническую подпись.
Алгоритм и условия неопределённости описаны в `doc/nat_detection.txt`.
`source=ETCP` обозначает результат детектора рабочего endpoint. Одно UDP-наблюдение может дать
адрес `TOPO_ADDR_NAT` при `mapping=UNKNOWN`, `inbound=UNKNOWN`: это NAT-кандидат
для пробного подключения, а не адрес интерфейса или подтверждённый открытый вход.
Общий внешний адрес подтверждает EIM; strict не публикует универсальный NAT-адрес.
Source входит в подпись; SOCKMETA занимает 5 байт. `source=STUN` означает предварительный
EIM? для того же локального IP/netif с неизвестным входом; измерение ETCP приоритетно.
Владелец снимает STUN-оценку после TTL. Внешний адрес тестового порта не публикуется:
NAT-кандидат по-прежнему требует наблюдения рабочего сокета.
Для TCP достаточно одного публичного пира: внешний IP с неизвестным входящим
портом публикуется как `TOPO_ADDR_NAT` с `port=0`, `mapping=UNKNOWN`, `inbound=UNKNOWN`.
NCD пропускает нулевые порты. Непубличный локальный TCP IP сразу означает NAT;
совпавший с наблюдением публичный IP даёт REAL_IP без подтверждения открытого входа.

Таблица `node_snapshots` хранит полную сериализованную запись без группового
окружения. Первичный ключ — полный X25519, числовой индекс допускает дубликаты.
Загрузка проверяет X25519 подписанного снимка. Поиск только по числу при совпадении
индексов двух ключей возвращает ошибку неоднозначности. `node_addresses.node_x`
ссылается на `nodes.x25519_pubkey` и хранит локальную проекцию адресов для поиска и отображения. При наличии сохранённого
snapshot загрузка использует его. Локальная публикация сохраняется до рассылки;
ошибка сохранения не разрешает публикацию новой версии.

`node_snapshots.format=3` отмечает NODEINFO с полными ключами без поля числового адреса. Открытие БД со старым первичным
ключом таблицы завершается ошибкой проверки схемы до запуска служб.
Пустые снимки не участвуют в классификации пиров; новый проверенный снимок может
заполнить такой кеш с тем же timestamp. Повторный запуск сохраняет новые снимки.

В проекции адресов сохраняются `nat_mapping`, `nat_inbound`, `nat_source`, `address_kind`.
Уникальность определяется endpoint и видом адреса,
а не отображаемым классом NAT. Старый производный формат пересоздаётся;
bootstrap-загрузка без подписанного snapshot не подтверждает NAT-профиль.
Такая загрузка требует хотя бы одного адреса; отказ SQL/памяти освобождает все частичные списки
и возвращает NULL. Наличие валидного snapshot с пустым списком адресов, напротив, допустимо.
При удалении старых `nat_evidence`/`nat_checked` адреса и REALITY сохраняются для bootstrap,
старые профили сбрасываются, сериализованные snapshots инвалидируются.
Максимальные timestamp snapshots сохраняются, чтобы новая локальная публикация
не откатывала версию даже при коррекции часов. Чат и ключи миграция не изменяет.

Timestamp 0 обозначает bootstrap-сведения без подписи (конфиг, приглашение,
начальные адреса). Они могут помочь установить первое соединение, но не
заменяют принятую подписанную запись. По BGP принимаются подписанные записи
с ненулевым timestamp. Формат NODEINFO изменён без обратной совместимости.

После принятия BGP-записи `node_conn_direct_update_node` применяет адреса к
существующему NCD-соединению. Отсутствующее соединение этот вызов не создаёт.
Путь подготавливается до изменения общего реестра и групповых подсетей: отказ
памяти сохраняет прежнюю запись, ссылки и пути. После commit IPv4-таблица
перестраивается для этого узла, включая удаление старых подсетей при пустом
новом наборе. Конфликт подсетей или OOM установки маршрутов логируется,
новый набор не устанавливается, прежние маршруты удаляются; ошибка запрещает
READY сессии. Принятая подписанная запись и пути при этом могут сохраниться.
Линки дополняются как при UP, так и до установления соединения; повторная
доставка не создаёт дубликаты UDP/TCP. Работающие линки не закрываются только
из-за смены списка адресов. NCD удерживает ссылку на общую запись, пока
обслуживает соединение, и использует её при восстановлении.
Для обхода адресов NCD делает отдельную копию: callbacks транспорта могут заменить
списки в общем реестре до завершения обхода. Удержание ссылки на запись сохраняет
сам объект, но не старые списки. Обновление, открытие и добавление нового сокета
используют общий подбор разрешённых пар: family, UDP/TCP, локальная политика,
NAT-профиль и обязательные метаданные REALITY. IPv6 link-local требует netif_index.
Новый сокет обслуживает NCD-транспорты вне FIN_WAIT; случайный выбор одного адреса не используется.

`node_conn_direct_open_node` сверяет переданную запись с реестром/БД. Более
свежая подписанная запись принимается целиком, старая уступает уже известной.
Bootstrap-адреса не перекрывают подписанную запись даже при DOWN.
ID узла проверяется по public_key. Ошибка запуска возвращает NULL handle и не снимает
прежний FIN_WAIT. Отдельно принятый snapshot и уже добавленные линки при частичной
ошибке могут сохраниться; новый handle публикуется после подготовки ресурсов.
Явный specific_sock задаёт локальную политику, сохраняя проверки family/протокола/цели/REALITY;
автоматическое появление сокета использует обычную политику подбора.

LAN discovery предоставляет отдельные адреса подключения и не меняет подписанный снимок.
Заголовок LAN discovery версии 2 содержит 32-байтовые Ed25519 отправителя и получателя.
В широковещательном объявлении адрес получателя нулевой. Объявление рабочих сокетов
и ответ на проверку подписаны. Получатель сверяет ключ с реестром, группой или SQLite.
Неизвестное устройство остаётся в списке discovery.
Обычные объявления имени, сообщения и ACK не подписаны и не подтверждают личность.
Общий UDP-порт 45731 принимает только объявления; unicast-обмен использует отдельные
ephemeral-порты. Формат и API описаны в `src/local_transport/protocol.h` и `local_transport.h`.

Подписываются весь заголовок local_transport (magic/version/type, длина, ключи/эпохи,
request=0) и тело: nonce(16), family(4/6), IP(16), количество сокетов,
затем socket_id/protocol/port(BE)/generation(BE) каждого сокета. IPv4 дополнен
нулевыми байтами. Подписанный IP обязан совпасть с источником UDP; рабочий порт
отдельный от discovery-порта. Публикуются принимающие IP/interface обычные сокеты,
без PRIVATE, probe и SOCKS UDP; до 32 endpoint на один IP, без фрагментации.

Объявление само не разрешает NCD использовать адрес. Только для узла без прямого UP
и живого BGP-пути во всех группах получатель отправляет случайный nonce;
подписанный ответ связывает его с обоими Ed25519 и эпохами discovery. Ответ принимается
однократно в течение 3 секунд. Это проверка свежести без часов/NTP: старые подписи,
эпохи или случайные поколения сокетов сами по себе свежесть не доказывают.
После проверки адрес действует 30 секунд по монотонным часам и только на интерфейсе
приёма (включая IPv6 scope). Повтор объявления/ответа не продлевает срок без нового nonce.
Дополнительно должен оставаться живым discovery-endpoint: только обычный ANNOUNCE
продлевает его собственный TTL 30 секунд; MESSAGE/ACK и подписанный обмен этого не делают.
Смена discovery-эпохи очищает endpoints и кандидаты. Проверка offline выполняется
при обработке подписанного объявления/ответа; чтение кандидатов её не повторяет
и само по себе не удаляет ранее проверенные адреса при появлении рабочего пути.
Сверка интерфейсов и периодические объявления выполняются каждые 10 секунд,
очистка TTL — по секундному tick или при запросе списка устройств/отправке сообщения.
Отключение broadcasts сохраняет unicast-объявления и ответы, приём и сроки жизни;
полная остановка discovery закрывает сокеты, завершает pending-доставки и очищает кандидаты.

NCD использует эти кандидаты при проверке совместимости, открытии/обновлении
и появлении локального сокета. Если сохранены только ключи, идентичность загружается
из nodes без требования старого адреса. LAN не создаёт NCD handle автоматически.
Неподтверждённые ETCP-пробы очищаются после истечения кандидата/остановки discovery;
после успешного handshake линк живёт по обычным правилам транспорта. REALITY требует
метаданных из известного снимка; прямые LAN TCP-пробы при глобальном SOCKS выключены.
Диагностика: discovery для подписи/nonce/адресов, etcp для NCD-проб и их удаления.

Конфигурационные подключения UTUN используют один адаптер
`init_client_connections` для старта и reload. Все адреса, TCP и REALITY
передаются NCD; адаптер не создаёт ETCP-линки. Новый набор handles открывается
до освобождения старого; при ошибке старые handles сохраняются. Конфигурация
удерживает один handle на клиента, независимо от количества его адресов.

Включение конфигурационного пира в UTUN-группу выполняет callback NCD UP.
Само событие транспортного UP не включает соединение в UTUN-группу автоматически.
Входящий JOIN остаётся явным запросом
участия. При пересоздании UTUN-группы учитываются её конфигурационные handles.
Удаление клиента отправляет `LEAVE_GROUP` и освобождает удержание UTUN-группы
с обеих сторон. Другие владельцы NCD сохраняют транспорт. Поздние NODEINFO и
WITHDRAW от отсоединённого UTUN-пира игнорируются, чтобы не вернуть его маршруты.
LEAVE ждёт backpressure через queue waiter и временно удерживает собственный
NCD handle. Закрытие транспорта отменяет ожидание; новое участие в группе
делает ожидающий LEAVE устаревшим, и он не отправляется.
Причина удаления пира передаётся явно: только потеря транспорта запускает
recovery каскадных маршрутов. Локальный/удалённый LEAVE и удаление битой
member-записи не должны восстанавливать намеренно закрытое участие.

REALITY использует полное SNI до 255 символов; размер поля в записи узла
согласован с транспортом. Если локального TCP listen-сокета нет, NCD может
создать исходящий TCP-линк с выбором локального адреса операционной системой.

Devgroup входит в общую подписанную запись: Ed25519/X25519 public keys,
удостоверение данного устройства, подпись профиля и исходные байты JSON.
В `nodes` хранятся `devgroup_ed`, `devgroup_x`, `devgroup_member_sig`,
`devgroup_json`, `devgroup_profile_sig`; отсутствие группы — NULL во всех пяти полях.
Проекция меняется вместе с `node_snapshots` в одной транзакции. Локальные секреты
находятся в `devgroup_local`, квитанции завершённого импорта — в `devgroup_receipts`.
Квитанции сохраняются после выхода: повтор передачи не восстанавливает членство.
Выбор имени: максимум (ver,timestamp,SHA256(JSON)) среди проверенных объявлений `nodes`.

NODEINFO упакован без выравнивания структур. Заголовок содержит uint16
`reality_size` и `devgroup_size`, затем прежние поля. После заголовка идут
`node_name_len` байт имени (без NUL), `devgroup_size` байт devgroup, metadata и адреса,
REALITY, опциональные подсети и список переходов. Пустой devgroup занимает 0 байт тела.
Непустой блок: Ed32, X32, удостоверение64, подпись JSON64, JSON без NUL (до768 байт).

REALITY: socket_id1, short_id8, server_pubkey32, version3, server_name_len1,
затем ровно server_name_len байт SNI без NUL. Прежний char[256] на проводе удалён.
Для SNI длиной N экономия составляет 255−N байт на сокет; `reality_size` добавляет
2 байта один раз в заголовке. Например, для example.com экономия244 байта на сокет.
Имя самого узла уже передавалось переменной длиной; его упаковка сохранена.
Парсер проверяет длину секции, число записей и отсутствие NUL внутри переданного имени.
Локальный GUI/JNI-снимок участника имеет свой формат, описанный в `chat_member.h`;
он не передаётся в BGP и не является NODEINFO.

## Порядок транспортов

В `[global]` принимающего узла задаётся `connection_order=TUR3`. Строка передаётся в NODEINFO
с собственной длиной, входит в Ed25519-подпись и сохраняется в SQLite-снимке (format=3).
T — обычный TCP, U — UDP, R — REALITY. Можно менять порядок и исключать протоколы; повторы запрещены.

* `TUR1`: первый совместимый протокол, без перехода при сетевой неудаче.
* `TUR2-4`: последовательные попытки по 4 секунды; предыдущие попытки отменяются.
* `TUR3`: все перечисленные протоколы одновременно.

Значение по умолчанию — `RUT2-2`: последовательные попытки REALITY, UDP и TCP по 2 секунды.

Для режима 2 таймаут задаётся целым числом секунд от 1 до 3600. Несовместимые протоколы пропускаются.
После полного неудачного прохода NCD сообщает TIMEOUT и повторяет проход, пока есть владельцы.
При потере связи перебор начинается сначала. Успех останавливает дальнейший перебор.
Без подписанного NODEINFO используется `RUT2-1`, независимо от неподписанных подсказок.

Qt и Android сохраняют собственную политику через настройки сети. Она применяется после перезапуска;
новая политика назначения не разрывает установленное соединение. Приём входящих соединений
и диагностические пробы доступности этой настройкой не ограничиваются.

## Локальные RTT

RTT не входит в подписанный снимок. `nodes.rtt` хранит среднее минимумов рабочих ETCP-линков
узла за интервал между сохранениями. `node_addresses.rtt` хранит аналогичную оценку только
линков к конкретному endpoint (семейство, IP, порт, протокол); разные локальные интерфейсы
участвуют в одном минимуме. PING/PONG служат резервным источником при отсутствии измеренных линков.
Единицы — 0.1 мс, NULL — замеров нет. Сохранение узла и адресов атомарно, не чаще раза в секунду.
Перепубликация NODEINFO сохраняет RTT адресной строки при неизменном полном ключе уникальности.
Новый адрес не наследует RTT старого. Живой RTT интерфейса берётся из выбранного группового пути.
