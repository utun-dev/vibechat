Ревью exit-прокси uTun, 20.11.2026

План по приоритетам и результаты

1. Закрытие TCP (4, 8). При отказе изменения мониторинга обработчик CLOSE
   учитывает синхронное удаление потока. При отказе выделения маркера CLOSE
   сокет и очереди освобождаются. Отложенная очистка сокета и потока
   резервируется до connect. В штатном случае маркер стоит после данных.

2. Проверка кодограмм (6). Клиент и сервер проверяют команду, направление и
   длину тела до изменения состояния. Пустое уведомление роутера закрывает
   потоки только в указанной группе и у указанного пира.

3. Открытие сокета (5, 7). Неблокирующий режим обязателен. Ошибка формата
   bind_ip, netif, so_mark или fib отклоняет конфиг. Корректное имя интерфейса
   хранится даже до его появления. Если ОС не применяет заданную настройку,
   конкретный CONNECT получает ERROR. Следующая попытка заново применяет настройки.
   При успехе connect сервер отвечает CONNECTED. При ошибке подготовки, connect
   или таймауте он освобождает ресурсы и один раз пытается отправить ERROR.
   Отказ отправки ERROR тоже виден в логе.

4. Группы (3). Повторяемый allowed_group задаёт весь список для TCP, UDP и ICMP
   exit. Без него разрешена только UTUN. Клиент принимает необязательный group=utun.
   Потоки, ответы, обратные вызовы и закрытие привязаны к группе. В CHAT требуется
   членство своего узла и пира. Пример конфига есть в src/proxy/tcp_proxy_server_doc.md.

5. Завершение half-close и квоты. Бездействующий TUN-поток освобождается после
   20 секунд ожидания в FIN_WAIT_2. Встречные DATA продлевают ожидание.
   Опции max_flows и max_flows_per_node учитывают вместе TCP, UDP и ожидающие
   ICMP-запросы во всех группах, по умолчанию 1024 на exit и 256 на узел.
   ICMP ждёт ответ 5 секунд от отправки каждого запроса. UDP-поток освобождается
   после 30 секунд без запросов клиента и ответов адресата.

На Linux проверены парсер и перезагрузка конфига, обработка команд, TCP/UDP/ICMP
и SOCKS/HTTP. В test_proxy_lifecycle проверены общие квоты, точные границы таймаутов, отказ
установки nonblocking и закрытие при нехватке памяти. В тесте двух групп
транспорт и допуск CHAT моделируются, а TCP и UDP сокеты настоящие.
Штатный клиент работает через UTUN. На стенде с тремя узлами прошли все
9 сценариев прозрачного прокси, передача с паузами и нагрузка из 8 параллельных
соединений. Valgrind для test_proxy_regressions завершился без ошибок и потерь памяти.
Общий check.sh останавливается на отсутствующем doc/group_isolation_matrix.txt.
При отдельном запуске 312 тестовых программ прошли 311. test_group_api_isolation
превысил время ожидания READY при подготовке групп. При первом отдельном повторе
таймаут повторился, при следующем тест прошёл. На исходном c1f3b52ce прошли
семь запусков. Связь таймаута с изменениями прокси не установлена.
Winsock-ветка TCP exit проверена кросс-компиляцией MinGW. Нативные прогоны на Windows
и FreeBSD остаются в задачах. Штатный Windows runtime пропускает запуск прокси.

Пункты ревью и их состояние

1. [x] Время жизни lwIP-потока при отправке DATA локальному exit.
   Очередь начинает отправку после возврата из lwIP recv. После локальной
   доставки отправитель заново находит поток по stream_id. Если ERROR уже
   закрыл поток, отправитель освобождает только принадлежащую ему запись.
   В test_proxy_regressions проверены возврат из recv с двумя фрагментами,
   немедленный ERROR при отправке первого и освобождение оставшегося фрагмента.

2. [x] Повторный вход в отправку буфера SOCKS при синхронном WINDOW.
   На время отправки фрагмента установлен общий для SOCKS и HTTP флаг sending.
   Вложенный WINDOW возвращает кредит, обработку буфера завершает внешний
   вызов. В test_proxy_regressions проверены точные байты, одна отправка DATA,
   восстановление окна, а также порядок DATA и FIN после ожидания кредита.

3. [x] Добавить в [tcp_proxy_server] повторяемую опцию разрешённой группы,
   по одной группе на строку. По умолчанию разрешена только группа UTUN.
   На клиенте выбирать одну группу, пока поддерживать только UTUN.
   Учитывать список до диспетчеризации TCP/UDP/ICMP и при уведомлениях
   о закрытии канала. Возвращать ответы в группу запроса, учитывать её
   в ключе TCP-потока и UDP-сопоставления, сохранять для ICMP-ответа.
   Проверить одинаковые peer и stream_id в двух разрешённых группах,
   раздельное закрытие и отбрасывание сообщений из посторонней группы.

4. [x] Обработать ошибку остановки чтения при TCP CLOSE. Если tcp_conn_pause_read
   через обработчик ошибки закрыл соединение, прекратить обработку CLOSE
   до следующего обращения к rc->tc.

5. [x] Проверять включение неблокирующего режима до connect. Обрабатывать
   незавершённый Winsock connect через socket_get_error и ERR_WOULDBLOCK.
   При ошибке явно заданных bind_ip, интерфейса, SO_MARK или FIB завершать
   попытку подключения и сообщать причину.

6. [x] Проверять длину тела TCP-команды до изменения состояния. CONNECT требует
   6 байт, WINDOW — 4, FIN/CLOSE/ERROR — 0, DATA — от 1 до TCP_PROXY_CHUNK.

7. [x] Отправлять ERROR при локальном отказе открытия TCP-соединения, в том
   числе при ошибках socket, bind и tcp_conn_create. Освобождать ресурсы
   частично созданного соединения и логировать причину отказа.

8. [x] Завершать поток при отказе выделения маркера CLOSE. Ошибка постановки
   маркера после остановки чтения должна приводить к освобождению сокета
   либо к гарантированному повтору.
